# Bee Call

An AI that phones you about your day. It reads what your Bee wearable picked up, calls your iPhone, talks with you in English over AirPods, hands slow work (research, calculations) to a background agent, tells you the result in two or three sentences, and saves the facts and todos you agree to back into Bee.

Status: work in progress for the Amazon "Build, Ship, Shape" hackathon (Bee track).

## How it fits together

| Part | Where it runs | What it does |
|---|---|---|
| iPhone app (`ios/BeeCall`) | your iPhone | Rings and takes calls with CallKit, joins the LiveKit room, shows live captions and the session screen |
| Voice server (`voice/`) | this Mac | LiveKit Agents: Amazon Transcribe (speech to text), the coordinator model, Amazon Polly (text to speech), turn-taking and barge-in; records every call |
| Coordinator | Anthropic's API, Amazon Bedrock | The voice you talk to: Claude Haiku 5.5 or Claude Sonnet 5.5, as each person chooses (`voice/claude_llm.py`, `voice/call_models.py`), with GLM 5 on Bedrock standing by |
| Worker (`worker/`) | AWS: Bedrock AgentCore Harness in Sydney | Background jobs, one folder per job; this Mac serves the harness's inline functions (progress, relay to the user, web search, saving result files) |
| Bee link (`beelink/`) | this Mac | Watches Bee for new conversations, saves raw context before a call, writes the facts and todos the user agrees to during it |
| AI-started calls (`voice/outbound.py`, `meta/agent.py`, `voice/dispatch.py`) | this Mac + LiveKit Cloud | The meta agent decides whether a Bee change or a call's end is worth offering a call; once the user says yes, the call room is opened and the app rings (`beelink/planner.py` is the older rule-based stand-in) |
| Session screen (`web/`, `voice/session_server.py`) | this Mac | Live view of a call: transcript, why the AI called, job cards |
| Token server (`voice/token_server.py`) | this Mac | Hands LiveKit room tokens to the app, tells an open app when the AI is calling, and serves everything else the app reads: the call list and each call's thread (`voice/call_view.py`), offers, voices and settings |

One server serves several people (`voice/people.py`). Each person has a folder, `data/people/<id>/`, and every call is kept there as plain files under `<date>/<time>/`: `transcript.md`, `events.jsonl`, `audio/` (raw audio, only while the person keeps audio on the server), `inputs/` (raw Bee data), `model-log.jsonl` (everything the call AI's model was given, never served), `claude-history.json` (what Claude was sent, never served), `prep.md` (the call prep note), `jobs/`, `bee-writes.jsonl` (each Bee write, with the question that named Bee and the user's answer), `usage.json`. The folder also holds `settings.json` (call language, evening call time, recording switches, daily budget, time zone) and the meta agent's files. A person's times follow their `time_zone` (an IANA name such as `Asia/Seoul`, the default), which the app sends from the phone: the suggested call time, quiet hours, the day's notifications and budget, call folder dates, booked times, and the time the AI is told. The person's own Bee login, once they connect Bee, sits outside it in `data/bee/<id>/`, where the meta agent's file tools cannot reach it. `data/` is not in git.

## Setup

Requirements: macOS, [uv](https://docs.astral.sh/uv/), Xcode 26 or later for the app, the [Bee CLI](https://www.npmjs.com/package/@beeai/cli) logged in to your Bee account, a [LiveKit Cloud](https://cloud.livekit.io) project, and an AWS account with Bedrock, Transcribe and Polly.

```bash
uv sync
brew install livekit-cli && lk cloud auth      # link your LiveKit project
lk app env -w                                   # writes LiveKit values into .env.local
aws configure --profile bee-call                # AWS keys stay in ~/.aws, never in this repo
python3 scripts/set_secret.py ELEVENLABS_API_KEY   # optional; input is hidden
```

`.env.local` holds `AWS_PROFILE`, `AWS_REGION` (Transcribe and Polly), `BEDROCK_REGION` (Claude) and the LiveKit values; see `.env.example`. Turn off "use of your content for service improvement" for AWS AI services before real calls, so Transcribe does not keep your voice.

## People

The app signs in with Apple. A new person waits until you approve them; the app shows a six-letter code:

```bash
uv run python -m voice.people waiting                 # sign-ins waiting, with their codes
uv run python -m voice.people approve 7F3K2A --as jiwoo   # refused if jiwoo is (or was) someone's id; add --same-person for a second Apple id of the same person
uv run python -m voice.people list                    # approved people and their settings
uv run python -m voice.people set jiwoo daily_budget_usd 2
uv run python -m voice.people remove jiwoo            # takes access away; the folder stays
uv run python -m voice.people session jiwoo           # prints a new sign-in token for jiwoo (black-box tests, support)
```

On a Mac, `uv run python -m voice.people add matt` approves a person for use from the Mac alone, and `BEE_CALL_DEV_PERSON=matt` in `.env.local` lets requests made on the Mac without a sign-in act as them when they carry the header `X-Bee-Call-Dev: 1` (curl, `voice.fake_caller`, `voice.agent console`). It is ignored on a server (where `BEE_CALL_PUBLIC_HOST` is set); never set it there anyway. A single-user `workspace/` from before moves in with `uv run python -m voice.people move workspace --to matt`; the worker's `state/harness.json` goes to `data/harness.json`, for everyone. Bee then has to be connected again for that person, since their login now lives in their own folder: turn on Use Bee in the app, or run `curl -X POST http://localhost:8787/bee/connect -H 'X-Bee-Call-Dev: 1'` and open the link it returns on the phone.

A person can use Bee Call without Bee (Use Bee off, the default until they connect Bee). Their calls never touch Bee: nothing is read from Bee before or during a call, the call AI has no Bee tools, and nothing the call AI, the prep or the meta agent is told mentions Bee. The AI asks about their day and works from their earlier calls and the meta agent's notes.

Each person's day has a budget (`daily_budget_usd`, 3 USD by default): an estimate from the calls' minutes and model use, background jobs and the meta agent (`voice/costs.py`). Past it (a spend equal to the budget counts as past it), the app's new calls are refused, and the voice server checks again when a call the user started begins; agreed AI calls are not placed, and the meta agent waits for the next day. The budget is checked only before a call starts: a call in progress is never cut. Whenever a call the user agreed to cannot be placed (the budget is used up, it is more than 10 minutes late, or placing it failed), a plain notification without buttons says so, once, in the person's language, for example "Couldn't place your 9:00 PM call: today's budget is used up."

## Run

```bash
uv run python -m voice.token_server                       # tokens for the app (port 8787; --host, --port)
COORDINATOR_LLM=anthropic uv run python -m voice.agent dev   # the voice server (ANTHROPIC_API_KEY in .env.local)
uv run python voice/session_server.py                     # the session screen (port 8788)
uv run python -m voice.outbound                           # watch Bee and let the AI call when it is worth it
uv run python -m beelink.writer data/people/<id>/<date>/<time>   # a call's Bee writes and how they went; --apply tries the failed ones again
```

The voice server joins only rooms it is dispatched to, as the agent `bee-call`. A call the user starts gets it through the app's token. A call the AI starts gets it from `voice/dispatch.py`, with metadata that says why the AI is calling; the voice server then waits up to 60 seconds for the phone to answer. The phone rings in two ways: an open app hears the call on the token server's `/ring` stream, and a closed or locked one gets an Apple VoIP push (`voice/voip_push.py`). When the user declines the call while it rings, the app sends `POST /calls/decline`: the voice server stops waiting within a second or so and records the call as declined, not missed, and `/ring` never replays it. For the push, create an APNs key in the Apple Developer account (Certificates, Identifiers & Profiles, Keys, with Apple Push Notifications service), keep the `.p8` file outside the repository, and set `APNS_KEY_PATH`, `APNS_KEY_ID` and `APNS_TEAM_ID` in `.env.local`. The app registers its push token with the token server (`POST /voip`) whenever it reaches it, and shows "also while the app is closed" once that worked. On a push, the app reports the call to CallKit at once, as iOS requires for every VoIP push, and a ring that already rang or expired is reported and ended.

Before the AI picks up, it reads the user's Bee data and writes itself a call prep note (`voice/prep.py`). The voice server reads Bee all at once (today's context, recent conversations, unconfirmed facts, todo suggestions, the conversations behind the call), and the coordinator's own model starts from that: it writes its opening line first, may take one round of up to three more Bee reads (a conversation in full, a search, another day's summary), then writes the note. For a call the user starts, the caller hears ringing from the voice server meanwhile, and the AI picks up when its opening is ready (within 6 seconds of the phone coming into the room, else with a fixed greeting); the ringing stops when the voice starts, and at most 8 seconds after the phone came; the note usually lands during the opening, and the first reply waits up to 2 seconds for one still being written. The app shows the call as connected only when the voice server sets the participant attribute `bee_call.state` to `answered`. A caller who hangs up before the AI's first words, or who never comes into the room (the voice server waits 30 s for the phone, as long as the app rings; the log says which of the two happened), leaves no call record and wakes no meta agent; the prep stops, and only what the call cost is kept (`state/spend.jsonl` in the person's folder). A phone that only lost the network is not a hang-up: LiveKit keeps the call for it to come back. For a call the AI starts, `voice/outbound.py` prepares before the phone rings, so the user never waits: the AI speaks as soon as the phone answers, and the Bee read the voice server makes meanwhile only feeds the call's record (and, for a call without a prep note, reaches the AI once it lands). Without a note, the coordinator gets the plain Bee context instead. During the call it can read more with its `bee_today`, `bee_conversation` and `search_bee` tools. `voice/outbound.py` prepares with the same model as the voice server, so set `COORDINATOR_LLM` (and `COORDINATOR_MODEL`) the same way for both: the prep runs on GLM 5 with `anthropic` and `bedrock`, and on the call AI's own model with `claude` and `nova`.

An ended call's record in the app has "Continue this call". The app asks the token server for a pass with that call's id (`/token?continue=<call_id>`, its LiveKit room; app builds from before design D send the record's folder, `<date>/<time>`), and the voice server starts the new call knowing what was said in the earlier one, what its background jobs found, and which jobs stopped unfinished when it ended (`voice/continuation.py`); the opening picks up from there. Nothing restarts by itself: a stopped job is only mentioned, and the user decides whether to run it again. The AI never calls back on its own to continue a call.

The meta agent below decides whether a Bee change is worth a call. The rule-based planner (`beelink/planner.py`) is a test stand-in that only `voice.outbound --rules` uses: a conversation with at least four utterances that ended within the last hour, or a new voice note; never during another call; at least 30 minutes after the last call or the last question. The watcher saves its Bee cursor only after a change was handled, so a change that could not be handled comes back on the next catch-up; likewise the meta agent's inbox moves on only after a think that worked, and a think that failed (the model unreachable) is tried again with the same events after 30 s, 1, 2, 5 and then every 15 minutes, never given up. Bee also records our own calls; for their time our call record is the source, so what Bee made of them (the conversation, the facts and todos made from it up to ten minutes after the call, and a voice note recorded during the call) is left out of the watcher's batches, a call's Bee reads and the AI's Bee tools (`beelink/calls.py`). A voice note recorded right after a call is the user's own and is kept.

Between calls, a meta agent decides what to propose (`meta/agent.py`). It wakes only for events, which any process appends to `data/people/<id>/meta/events.jsonl`: a Bee change (from `voice/outbound.py`'s watcher), a call that ended, and an AI call the user missed or declined while it rang (the voice server), the user's answer to an offer (the token server), and a booked call ten minutes away. Each person has their own meta agent, which sees only their folder and their Bee. It looks at what changed with read-only tools, `list_files`, `read_file` and `grep` over the person's folder (never outside it, never push tokens or audio) and the Bee read tools, and then it may offer a call, rewrite its notes (`meta/state.md` in the person's folder: open threads, the agenda for the next call, what the user turned down, what they prefer), or do nothing. It only proposes: calls wait for the user's yes, and Bee changes go on the agenda for a call. Offer notifications never go out during a call, wait 30 minutes after a call ends (answered, missed or declined) and after the last offer notification, and are held between 23:00 and 08:00; a held offer shows in the app's list at once, and its notification goes out once it may. At most four go out a day: a fifth offer shows only in the app's list. Every time it thinks, the meta session (`meta/session.jsonl`) keeps the events, every tool it used and its own words, and the session screen shows them as they are under "Between calls". Each call's prep reads the notes. `uv run python -m probes.meta_probe` shows how the model judges three made-up moments in a scratch workspace. `voice/outbound.py --rules` uses the old rule-based planner instead.

The AI never rings on its own: it asks first (`voice/offers.py`), and about one Bee conversation at most once, also after the user declined. A call decision becomes an offer, sent as a plain notification such as "About “Planned a Saturday hike”: free for a quick call at 9:00 PM today?", with three buttons: at the suggested time, now, or not now. It shows on the lock screen and on Apple Watch, and the app's first screen lists open offers too. A button sends the answer to the token server (`POST /offers/<id>`) even while the app is closed, and `voice/outbound.py` places the call when the user tapped "now", when the accepted time comes (prepared 30 seconds early), or at a time the user booked out loud in a call (the coordinator's `book_call` tool; that call continues the call it was booked in; a time like "in ten minutes" counts from when it is said, and the AI reads the booked time back). The suggested time is the person's `call_time` setting (21:00 by default; tomorrow when today's is less than ten minutes away). The app registers its notification token with `POST /push`. Try one offer without Bee events with `uv run python -m voice.outbound --once data/people/<id>/inbox/<folder> --person <id> --any-age --no-cooldown`: it asks, then waits for the answer and places the call. A call the user said yes to can be called off (the app's "Call off", `POST /offers/<id>` with `decline`) until its room is being made: the offer is checked once more right before that, and nothing rings for a call that was called off.

Each person's `language` setting picks their call language: `en` (the default, and the demo) or `ko` (`voice/language.py`); the app changes it with `PUT /settings`. It sets what Amazon Transcribe listens for, the Amazon Polly voice (Ruth or Seoyeon), the language the coordinator speaks and the prep's opening line; the rest of the instructions stay in English, and LiveKit's turn detector follows the transcript's language. One call is in one language, since Transcribe listens for one language per stream. Try Korean without a phone with `uv run python -m voice.fake_caller --language ko`.

Each person picks the AI's voice in the app (setting `voice`, read as a call starts) from the voice catalog, `voice/voice_catalog.json`: for each call language its voices in the order the app lists them, the default first, each with a provider-independent id (`ko-sian`), its own name, one word for how it sounds in Korean and English, its provider's voice (ElevenLabs), a sample the app plays (`voice/voice_samples/`, named by its content's hash; the token server's `GET /voices` lists them and serves the samples to anyone), and server-only speech tuning tuned by ear (`stability` so far). `voice` holds a catalog id of the call language's voices, or null for the default, and a change of language alone resets it unless it fits; the old `tts` setting is retired and a provider voice id set by hand reads as its catalog id. ElevenLabs needs `ELEVENLABS_API_KEY` with the Text to Speech permission; `ELEVENLABS_MODEL` is `eleven_v4_turbo` when unset: the most expressive of ElevenLabs' fast models and, measured from Seoul, about as quick to its first sound as `eleven_flash_v2_5` (0.15-0.24 s against Polly's 0.8-1.1 s). `ELEVENLABS_STABILITY` (0 to 1) makes a voice livelier when lower, for voices whose tuning does not set it. A machine without the ElevenLabs key, or with `TTS=polly`, speaks every call with Amazon Polly (Ruth, or Seoyeon for Korean, or `POLLY_VOICE`), and the call's `coordinator` event says which voice spoke (`voice/voices.py`). To compare voices, `uv run python -m probes.voice_samples` has real call lines read by the Polly voices and your ElevenLabs voices, on the path a call uses, and writes a page to listen to them side by side with each sample's time to first sound (`--list` shows your ElevenLabs voices, with the Voices read permission).

`COORDINATOR_LLM` picks what answers in the coordinator slot (`echo` when unset, for the voice server, `voice/outbound.py` and the meta agent alike; `voice/call_models.py` reads it):

- `anthropic` (the server's default): Claude on Anthropic's own API, with the key in `ANTHROPIC_API_KEY`. Each person picks the model in the app (setting `call_model`, read as a call starts): `haiku`, the default, is Claude Haiku 5.5 with adaptive thinking and effort `low` (with thinking off it skipped booking a call it promised in 3 of 6 probe calls); `sonnet` is Claude Sonnet 5.5 with thinking `between_tools` (it refuses `disabled`) and effort `low` (`voice/call_models.py`, the one place that maps the choice). `COORDINATOR_MODEL`, `COORDINATOR_THINKING` and `COORDINATOR_EFFORT` are not used in this mode; a call that finds one set logs it and lists it in its record's `coordinator` event (`settings_not_used`). The system prompt and the growing history are cached, and the record's `coordinator` event names the model. GLM 5 on Bedrock stands by: without a key, or when the first request of a call fails (no network, a refused key, no credit left, a rate limit, an outage), GLM 5 answers it and the rest of the call. A decline is not a failure and is never handed to GLM 5. The call's `events.jsonl` has a `coordinator_model` line with the model that answered, and why when it is not Claude. After the first answer the call keeps its model; a later failure is a failed turn, as with any model. When Claude declines a turn (`stop_reason` `refusal`), the caller hears one short line in the call's language and the call goes on (`claude_refusal` in the record); what came in with the declined request (the caller's words, a tool's result, the app's notes) is left out of later requests, so it is not declined again turn after turn. The prep and the meta agent stay on GLM 5.
- `claude`: Claude on Bedrock through the same adapter (Claude Sonnet 5.5, or the Bedrock model id in `COORDINATOR_MODEL`; set `COORDINATOR_THINKING=disabled` for Claude Haiku 5.5). Claude is blocked on this AWS account for now.
- `bedrock`: a Bedrock model through the Converse API, `COORDINATOR_MODEL` (GLM 5 when unset).
- Test stand-ins: `fake`, the real Claude adapter with scripted replies and no network (it checks every request against the Messages API rules and checks that earlier turns were never edited, so you can test barge-in, tools and job results; say "test job" to start a background job); `nova`, Amazon Nova 2 Lite, a model that can call tools; `echo`, which repeats you (say "test job" to exercise the background job flow).

Every call saves `model-log.jsonl`, whatever the model: one line per request the call AI's model received, with the model that answered it, the whole chat as LiveKit gives it (the instructions, both sides, every tool call and its result), the tools offered, and what came back, for debugging. When Claude answered (`anthropic`, `claude`, `fake`), a call also saves `claude-history.json`, exactly what was sent to Claude. Both stay on the server: they hold Bee data, and the record server never serves them.

`WORKER` picks what runs delegated jobs: `harness` is the AgentCore Harness worker (`worker/harness.py`; create it once with `uv run python scripts/deploy_worker.py --smoke`), `search` answers each job with one Amazon Nova Web Grounding search (`worker/web_search.py`), and `fake` (the default) pretends to work for a few seconds. The last two are test stand-ins. A web search costs about 0.03 USD; try one on its own with `uv run python -m worker.web_search "your question"`.

The harness runs the agent loop in AWS; when the agent calls one of its inline functions, the harness stops and hands the call to this Mac, which runs it and sends the result back in the same session. Result files go straight into the job folder on this Mac through `save_file` (text) and `save_chart` (numbers, drawn here as SVG), so the job folder has one writer. The coordinator hears about a job the way Claude Code tells its model about a background task: `delegate` returns a job number at once, and the job's news arrives later as a `<job-notification>` block (job number, status, task, and a summary, an error or the files it made). The answer the worker relays comes while the job still runs, so the user hears it before the report is written, and the job's end follows with its files. However a job ends, the user hears about it: a job that never relayed anything ends with its summary, and a failed job with its error. The coordinator can also check on running jobs with its `job_status` tool. Until Claude on Bedrock is available for the account, the harness uses GLM 5 (`WORKER_MODEL` or `--model` changes it), with its reasoning on (`reasoning_effort` `high`). Background jobs need not be quick, only the call AI's replies: a job may take up to 80 round trips through this Mac, each up to 30 minutes and 120 steps, and write a report of up to 32K tokens in one model call (GLM 5 on Bedrock holds 202,752 tokens of prompt and answer together, so this leaves the job's conversation about 170K). A job still stops when its call ends; a later call that continues it hears that it stopped unfinished.

### iPhone app

Open `ios/BeeCall/BeeCall.xcodeproj` and pick your team under Signing. The server address comes with the build: the target's `BEE_CALL_SERVER` and `BEE_CALL_RECORDS` build settings fill `BeeCallServer` and `BeeCallRecords` in `Info.plist`. A Debug build talks to the Mac (run it on a device on the same Wi-Fi; the first screen has a field for the Mac's address, `http://<Mac LAN IP>:8787/token`, and the call record comes from port 8788 on the same host). A Release build, the one TestFlight gets, talks to the cloud server only, with no field. A Debug build opens the call record page with `?debug=1`, which shows its "Show debug events" switch; a Release build never does.

The app signs in with Apple (`SignInView.swift`, `Server.swift`) and keeps the server's sign-in token in the Keychain; a new person sees a code to send to whoever runs the server. The rest of the person's choices live on the Bee Call page of the iOS Settings app (`Settings.bundle`): call language, evening call time, whether call audio is saved on the server and on the iPhone, and "Use Bee". The app sends them to the server whenever it comes to the foreground, and turning on "Use Bee" opens Bee's approval page for the person's own Bee account. The token server waits about five minutes for that approval, also across its own restart (`data/bee/<id>/pending.json`); a second connect stops the first one's wait before it starts. Turning "Use Bee" off removes the person's Bee login from the server, also when `bee logout` fails, and answers 204 only once it is gone. With "Save on this iPhone" on, the app records the call itself (LiveKit's `AudioMixRecorder`: the microphone and the AI's voice in one file) into the Files app under On My iPhone, Bee Call.

### What the app reads

The app draws what the token server builds, and `contract/app-contract.md` names every endpoint and field it uses, with a JSON Schema for each body and an example of each in `contract/` (`uv run --with jsonschema python contract/check.py` checks them). `voice/call_view.py` is the one place that turns a person's call records into the call list (`GET /calls`, newest first, with what each folded call shows) and one call as its thread (`GET /calls/<call_id>`): the speech as bubbles, job and Bee write cards where they happened, why the AI called, what it looked at in Bee before it picked up. A call's id is its LiveKit room. Its files come from `GET /calls/<call_id>/files/<path>` by the session screen's rule (never audio, raw Bee data or what the model was given). The list, a call and the offers carry a version as their ETag and answer 304 when unchanged, and `GET /changes` (Server-Sent Events) says which of them changed, so an open app fetches only that. `GET /voices?language=ko` lists the voices to pick from. The tests write `contract/examples/` from the fixture records in `tests/fixtures/sessions/`, so the examples are what the code answers.

Three things feed it from the voice server and the worker: while a call runs its record shows life every 30 seconds, so a quiet call never reads as dropped; after a call, one Claude Haiku 5.5 request (at most 5 s, only when the person spoke) writes its one-line title (`voice/titles.py`); and a chart a job draws gets a PNG beside its SVG (`worker/chart.py`), since the app cannot show SVG. For records from before these: `uv run python -m voice.titles data/people/<id>` titles the person's ended calls without a title, and `uv run python -m worker.chart data/people/<id>` draws their charts' missing PNGs.

## Testing from outside

Ways to drive and watch Bee Call without the iPhone, AWS or a real Bee, for black-box tests. None of them lets a call ring without the user's yes.

- **Port and address.** `python -m voice.token_server --host 127.0.0.1 --port 18787` (the port defaults to `TOKEN_SERVER_PORT`, or 8787).
- **An offer.** `python -m voice.offers ask <person> --topic "Planned a Saturday hike" --reason "Dana asked about Saturday." [--conversation <Bee id>]... [--at 20:30]` makes an offer the way the meta agent does, without its model, under the same rules (one question at a time, one offer per Bee conversation), and prints it as `GET /offers` shows it. Its notification goes out from `voice/outbound.py`'s loop, as a held one does. Nothing rings until the user answers yes (`POST /offers/<id>`).
- **A Bee change.** `voice/outbound.py` watches Bee through the CLI named by `BEE_BIN`, so a stand-in CLI can report changes. It runs `bee stream --json --types new-conversation,update-conversation,update-conversation-summary,journal-created,journal-text`, which prints one JSON object per line, `{"event": "<type>", "data": {...}}`; `update-conversation-summary`, `update-conversation` and `journal-created` start a catch-up 20 seconds after the last of them. A catch-up runs `bee changed [--cursor <cursor>] --json`, which answers `{"conversations": [{"id", "start_time", "end_time", "short_summary", "utterances_count"}], "facts": [{"id", "text", "created_at"}], "todos": [...], "journals": [{"id", "text", "created_at"}], "dailies": [...], "meta": {"next_cursor": "<cursor>"}}` (times in epoch milliseconds). What it found, minus what Bee made of our own calls, is saved as `inbox/<date-time>/changed.json` in the person's folder (the same object, with `left_out_as_our_calls` counting what was left out), which `python -m voice.outbound --once <that folder>` also takes.
- **Pushes.** Every notification and VoIP push the server sends, or would send, is a line of `state/pushes.jsonl` in the person's folder: `{"at", "type": "alert" | "voip", "payload", "sent", "status", "apns_id", "reason"}` (`reason` says why one did not go out, for example `APNs is not configured`; never a device token or a credential). `APNS_URL=<base URL>` sends pushes to a test receiver instead of Apple (`<base URL>/3/device/<token>`, plain HTTP allowed; a signing key is still needed, `APNS_KEY_PATH`, `APNS_KEY_ID` and `APNS_TEAM_ID`, which any P-256 key will do for a receiver that does not check it). The server never takes `APNS_URL` from SSM.
- **A waiting sign-in.** `python -m voice.people test-sign-in [--email E]` makes what a first Sign in with Apple leaves, for a made-up Apple id, and prints `{"code", "sub"}`. It waits like any other: `approve CODE --as ID` approves it, and `session ID` then prints the token the app's next sign-in would get (the app gets no token while it waits).
- **A test clock.** `BEE_CALL_CLOCK_FILE=<path>` names a file holding one ISO 8601 time with its zone, such as `2026-10-15T20:55:00+09:00`. From the moment the file is written, every process that has the setting believes it is that time, and the clock runs on from there; write the file again to set it again. A missing file, or one that holds anything else, leaves the real clock. Everything that is "the user's time" follows it: the suggested call time, quiet hours, the day's notifications and budget, call folder dates and booked times. The server never takes this setting from SSM.

## Privacy

Each person sees only their own calls: the token server and the session screen work in the signed-in person's folder, the voice server records into it, and the meta agent and Bee reads stay inside it. A phone's push tokens belong to the person signed in on it (`data/devices.json`, one owner per token): signing out takes them away, another person who signs in on that phone takes them over, and `voice.people remove` drops them. Raw call audio is kept in the call's folder while the person's `record_on_server` setting is on (the default), read again when the phone answers; with it off, or when the person's settings file cannot be read, only the transcript and the record are kept. LiveKit's own session recording is off in code (`record=False`), whatever the LiveKit project's setting, and every call job tells LiveKit so as it starts, so a call that never gets a session (missed, declined, refused over budget, hung up while it rang) has none of its logs uploaded either. The session screen never serves raw audio (`audio/`), raw Bee data (`inputs/`) or what the model was given (`model-log.jsonl`, `claude-history.json`). Bee data is read through the official Bee CLI, with each person's own login. Nothing is written to Bee unless, during the call, the AI asked a question that names Bee and the item ("Shall I add 'note the bug' to your Bee todos?") and you said yes. The AI fixes the item before it asks (`propose_bee_save`), the question quotes the item whole, and only your answer right after the first such question counts (to ask again, the AI proposes the item again), so no write rides on an earlier yes, on a yes to another question, or on a question the AI asks while it saves. An answer in which a sentence starts by saying no is never taken as a yes; the AI asks about the item alone. After the yes the item is written at once, the AI says what it wrote, "take it out" undoes the last write, and each write keeps that question and your answer in the call's `bee-writes.jsonl`. A write that ends with an error is said in the call and tried again after it; since the Bee CLI also reports an error when Bee stored a todo and only its answer was lost, Bee is first asked whether it has the todo already, and a todo Bee cannot be asked about is not written again. A write Bee may have taken without saying so (it did not answer in time, or it was cut off mid-write) is never written again by itself, so no todo is made twice; the AI says to check Bee, or, when the call had already ended, the notification does. One notification after the call lists what went into Bee and what to check.
